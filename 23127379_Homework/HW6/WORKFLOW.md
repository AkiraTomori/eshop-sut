# HW06 API Testing — Working Guide

This guide instantiates the tool-neutral workflow defined in the repository-root `AGENTS.md`. The command templates are prompts under `.agents/commands/`; they are not shell scripts and are not tied to a specific AI product.

## Authoritative sources

1. `AGENTS.md` — workflow, gates, scope, and state rules.
2. `2026.HW06.API Testing_En.md` — assignment requirements and submission rules.
3. Repository-root `README.md` — SRS/business rules.
4. Repository-root `api_specification.md` — endpoint contracts.
5. `.agents/skills/api-skill/state/progress.md` — current workflow state.

## Selected APIs

| Pool | API unit | Endpoint(s) |
|---|---|---|
| A | FR-03 password recovery | `POST /api/forgot-password`, `POST /api/reset-password` |
| B | FR-08 checkout | `POST /api/checkout` |
| C | FR-15 update product | `PUT /api/products/:id` |

No GET endpoint may be designed or executed as an HW06 test.

## Working sequence

### Pool A

1. `/domain-test pool-a` — deeply inventory and partition every relevant parameter.
2. `/state-transition pool-a` — model the OTP lifecycle and every state × event combination.
3. `/security-check pool-a` — applicable SEC-01–SEC-07 plus response schema.
4. Review all proposals and enter `confirm stage 1` only as each applicable technique is accepted.
5. `/audit pool-a` → `confirm stage 2`.
6. `/extend pool-a` → review at least five new cases → `confirm stage 3`.
7. `/build-postman pool-a` → review artifacts/real local evidence → `confirm stage 4`.
8. `/bug-report pool-a` → triage real failures → `confirm stage 5`.
9. `/next-pool` after Pool A is DONE.

### Pool B

Use the same five stages with this Stage 1 order:

`/domain-test pool-b` → `/decision-table pool-b` → `/security-check pool-b`

Then continue with `/audit pool-b`, `/extend pool-b`, `/build-postman pool-b`, `/bug-report pool-b`, and `/next-pool`.

### Pool C

Use this Stage 1 order:

`/domain-test pool-c` → `/security-check pool-c`

Then continue with `/audit pool-c`, `/extend pool-c`, `/build-postman pool-c`, and `/bug-report pool-c`. Pool C has no successor.

### Finalization

1. `/cicd-setup` — propose the workflow; the user supplies two real runs and enters `confirm ci/cd`.
2. Complete the self-drawn test-generator diagram and retain authorship evidence.
3. `/critique` — compile real audit evidence and the 200–300 word critique → `confirm critique`.
4. `/finalize` — reconcile every artifact and compile the final package → `confirm finalization`.

## Evidence boundaries

- The student must capture the real `X-Student-Id` console screenshot.
- Newman output and hostname must come from a real run.
- CI/CD URLs and screenshots must come from two real commits/runs.
- The test-generator diagram must be drawn by the student, not generated by AI.
- GitHub Issues require user review, real screenshots, and manual posting.
- Missing evidence remains `[USER ACTION REQUIRED]`; it is never synthesized.

## Per-pool handoff

Each pool's `pipeline.md` is the working index. Store or link the confirmed Stage 1 tables, Stage 2 audit, Stage 3 additions, final Excel/CSV cases, Postman artifacts, Newman report, screenshots, and bug evidence there. A later stage may use only confirmed prior-stage artifacts.
