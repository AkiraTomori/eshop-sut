# Pool C / FR-15 — Security & Schema Checklist Proposal

> Scope: `PUT /api/products/:id` only. This is a Stage 1 proposal. No payload has been sent, no API or GET request has been executed, and no vulnerability is claimed.

## Specification basis, fixtures, and safety rules

- Business authorization: root `README.md` §FR-12 requires a valid JWT and `role = 'admin'` for every data-changing Product API.
- Product integrity: root `README.md` §FR-15 requires `name` (maximum 255 characters), numeric `price > 0`, an existing category, and mutation of only the selected product.
- Security requirements: root `README.md` §SEC-01–SEC-07. Applicability is assessed individually below; non-applicable requirements are not converted into fabricated product rules.
- Endpoint contract: root `api_specification.md` §3.3 documents `PUT /api/products/:id` and a JSON body containing `name`, `price`, `description`, `imageUrl`, and `category_id`. It specifies no response status, Content-Type, success/error body, field type, nullability, or error precedence.
- Display sinks: `README.md` §FR-05/FR-06 shows product name, image, description, and category in the UI. The PUT boundary can test reflection and persisted-data handling, but render-time escaping cannot be proven through this endpoint alone. That part remains a human/white-box evidence gate, not a GET test.
- Fixtures reuse the confirmed Domain proposal's symbolic `A1` admin JWT, `U1` normal-user JWT, target product `P1` (`id=101`), distinct product `P2` (`id=102`), non-target set `P3+`, existing categories `C1`/`C2`, headers `H0`, and valid body `B0`. Tokens and IDs are test-controlled placeholders, not real secrets or current database claims.
- Each mutating case uses a fresh disposable fixture or a rollback. State protection is checked with approved restricted datastore snapshots or another non-GET oracle. Setup failures, stale fixtures, missing evidence, or unavailable render sinks are harness/evidence problems—not SUT defects.
- Exact HTTP codes and response schemas are absent, but the requirements support HTTP-class oracles. A valid documented update expects `2xx`; required authentication, authorization, validation, path, and missing-target failures expect `4xx`; inputs governed by an undocumented parser/additional-property/override policy use an explicit `2xx/4xx` branch. Concrete codes and response fields remain contract gaps rather than guessed values.
- Future Stage 4 requests, including any fixture-only requests later approved, must receive `X-Student-Id: {{StudentID}}` from the collection-level pre-request script. No real student ID is hard-coded here.

## Proposed checklist test cases

Unless stated otherwise, send `PUT /api/products/101` with `A1`, `H0`, `B0`, existing `P1`, `C1`, and a pre-state snapshot of `P1`, `P2`, and `P3+`. Rejection means a `4xx` response and no product changes. Acceptance means a `2xx` response and only the path-selected target receives documented fields; product count, user roles, categories, and every non-target product remain unchanged. For a branch oracle, the observed state must match the returned status class.
