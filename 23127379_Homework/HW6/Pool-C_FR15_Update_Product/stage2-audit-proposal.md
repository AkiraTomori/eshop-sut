# Pool C / FR-15 — Stage 2 Test-Case Audit

> Audited sources: `README.md` FR-12/FR-15 and SEC-01–SEC-05, `api_specification.md` §3.3, `stage1-domain-testing-proposal.md`, and `stage1-security-schema-proposal.md`. This audit preserves all 86 Stage 1 IDs and assigns the required final `VALID / INVALID / INCOMPLETE` label without claiming execution.

## Audit rules applied

- `VALID`: the primary oracle is directly traceable to `README.md`, `api_specification.md`, or a correctly narrowed Stage 1 oracle. The absence of an exact numeric HTTP code does not invalidate a case when Stage 1 supplies the source-supported `2xx`/`4xx` class and a decisive mutation/security oracle.
- `INVALID`: the case contradicts or leaves the selected `PUT /api/products/:id` scope.
- `INCOMPLETE`: the case's primary pass/fail verdict still depends on an undocumented identifier/media/parser/optional-field/response/rendering rule or lacks an observable sink. An explicit two-branch characterization oracle is useful, but it does not become a conformance test until the governing policy is confirmed.
- A missing `:id` segment remains a valid negative partition of the documented route template when its oracle is limited to a `4xx` route-class response and no mutation; it is not treated as selection of a second business API.
- These are final Stage 2 audit labels. No GET case, API request, or Newman execution is introduced.
