# Pool A / FR-03 — Stage 2 Test-Case Audit Proposal

> Audited inputs: the confirmed Domain Testing, State Transition Testing, and Security/Schema Checklist artifacts for `POST /api/forgot-password` and `POST /api/reset-password`. The source cases were not edited, deleted, merged, or approved by this audit.

## Audit basis

- Assignment: `23127379_Homework/HW6/2026.HW06.API Testing_En.md` §6 requires at least 35 reviewed cases, security and state coverage, and exact response-schema checks.
- Business rules: root `README.md` §FR-03, password rules inherited from §FR-01, and §9 SEC-01 through SEC-07.
- Endpoint contract: root `api_specification.md` §§1.3–1.4.
- The forgot-password success oracle is specified: status `200`, exact `message`, and string `resetToken`; FR-03/SEC-07 further require six decimal digits.
- The reset-password success status and response schema, every error status/schema, response `Content-Type`, concrete OTP TTL, retry policy, token retention after failed attempts, and old-token behavior after reissue are absent. Per the audit skill, a case depending on one of these gaps is `INCOMPLETE`, even if its core rejection or state-protection intent is correct.
- No case uses GET, an out-of-scope endpoint, or a duplicated ID. Four state rows contain no request; they are retained in the audit copy but cannot be complete API tests without an observable oracle.

## Audit warnings and disposition

- Both scoped endpoints are covered: forgot-password appears in 20 request cases and reset-password in 55 request cases; four state rows are wait/no-request rows.
- The raw count exceeds 35, but only six cases are currently complete under the strict audit definition. The 73 `INCOMPLETE` rows should not be converted into fabricated HTTP/schema assertions; their contract gaps must be confirmed or their scope narrowed to independently specified state/security oracles.
- No `INVALID` label is proposed because no row contradicts an explicit requirement, uses GET, leaves Pool A, or duplicates an ID. Several state rows are multi-condition or non-observable and are therefore `INCOMPLETE`, not silently deleted.
- Domain coverage inventories every documented request field and supported boundary. The confirmation-password UI/API mismatch, response media types, error contracts, reset response, OTP TTL, retry/retention, and reissue behavior remain explicit gaps.
- Any future Postman/Newman implementation must apply `X-Student-Id: {{StudentID}}` through the collection-level pre-request script; the real student ID must not be hard-coded.
