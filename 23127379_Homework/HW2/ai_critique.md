## 2. A.I Critique
Firstly, from a positive perspective, A.I has greatly assisted me in the process of designing draft test cases. A.I has a strong ability to read and understand text, and my role is to provide A.I with the necessary tools so it can comprehend context and grasp the relevant theories in the Black-box testing section. Moreover, A.I has provided significant support in designing test cases and compiling summary reports. These are the positive aspects. On the other hand, the A.I I am currently using can only understand static documentation. The issue here is that when executing the content of FR08, the initial draft generated by A.I suggested shifting focus to FR09. I have identified this and requested that A.I remove the content of FR09 from FR08 because proceeding otherwise would result in overlapping functionalities. This issue is what I call A.I making problems more complex, leading to unnecessary content generation. Additionally, A.I only understands static documents; thus, when provided with existing documentation, it generates highly comprehensive test cases covering UI and API aspects. However, a challenge A.I has not yet mastered is its ability to execute API test cases without requiring Human-in-the-loop intervention. Furthermore, for UI observation-related test cases, A.I cannot perform them autonomously and requires Human-in-the-loop involvement for 100% manual execution. Therefore, the principle I have derived from working with A.I is that while it excels at creating and generating drafts for review, it must be monitored and cross-referenced with documentation to prevent over-engineering issues. It may be beneficial to develop additional sub-skills for A.I so it can fully replace human effort in executing API-related test cases, allowing students to focus on UI testing or utilize specific tools/Frameworks for testing purposes.
