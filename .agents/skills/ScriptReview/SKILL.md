## Skill Purpose

## Review Checklist (Run in Order)

### Check 1 — Test Data Separation

```
□ No hardcoded string literals inside test() bodies (URLs, credentials, input values)
□ All test data read from fr##-test-data.json via import
□ Test data file is a valid JSON file (run: node -e "require('./fr##-test-data.json')")
□ fringe check: are dynamically computed values (e.g., "A".repeat(255)) noted in comments?
```

**Common AI failure:** AI often hardcodes values like `page.fill('input', 'Laptop Gaming ABC')` instead of `page.fill('input', tc.inputs.name)`.

### Check 2 — Locator Quality

For every `page.locator(...)`, `page.getByRole(...)`, etc., evaluate:

| Locator Type | Risk Level | Recommendation |
|-------------|-----------|----------------|
| `page.getByRole('button', { name: ... })` | ✅ Low | Preferred — accessible |
| `page.getByLabel('...')` | ✅ Low | Preferred — form fields |
| `page.getByText('...')` | ✅ Low | Good for text elements |
| `page.getByPlaceholder('...')` | ✅ Low | Good for inputs |
| `page.locator('[data-testid="..."]')` | ✅ Low | Good if app uses data-testid |
| `page.locator('.class-name')` | ⚠️ Medium | Fragile if CSS changes |
| `page.locator('#id')` | ⚠️ Medium | OK if IDs are stable |
| `page.locator('div > span:nth-child(2)')` | ❌ High | **Fragile — flag for fix** |
| `page.locator('//xpath/expression')` | ❌ High | **Fragile — flag for fix** |
| `page.$('css > chain > deep')` | ❌ High | **Fragile — flag for fix** |

**Document every fragile locator:**
```markdown
### [ISSUE] Fragile Selector — Test: TC-FR##-EP-001
- **Location:** fr##.spec.ts line XX
- **AI-generated:** `page.locator('div.product-detail > div:nth-child(3) > span')`
- **Risk:** Will break if DOM structure changes (e.g., new wrapper div added)
- **Fix applied:** `page.locator('[data-testid="product-price"]')` or `page.getByText('₫')`
- **Reason AI failed:** AI predicted DOM structure without inspecting live SUT
```

### Check 3 — Assertion Strength

Evaluate every `expect()` call:

| Assertion | Strength | Issue |
|-----------|----------|-------|
| `expect(page).toHaveURL(exact)` | ✅ Strong | |
| `expect(locator).toHaveText(exact)` | ✅ Strong | |
| `expect(locator).toHaveValue(exact)` | ✅ Strong | |
| `expect(locator).toBeVisible()` | ⚠️ Medium | Does not verify content |
| `expect(locator).toContainText(partial)` | ⚠️ Medium | May be too lenient |
| `expect(locator).toBeEnabled()` | ⚠️ Weak alone | Needs content assertion too |
| *(missing assertion after action)* | ❌ None | **Flag — action without verify** |

**Document weak assertions:**
```markdown
### [ISSUE] Missing/Weak Assertion — Test: TC-FR##-EP-003
- **Location:** fr##.spec.ts line XX
- **AI-generated:** Click "Add to Cart" → only checks `toBeVisible()` on toast
- **Issue:** Does not verify: (a) toast message text, (b) cart badge count, (c) API response
- **Fix applied:** Added `expect(toast).toContainText('đã được thêm')` + `expect(cartBadge).toHaveText('1')`
- **Reason AI failed:** Prompt did not specify all assertion requirements from HW2 TC expected result
```

### Check 4 — Flaky Waits

Search for prohibited patterns:

```bash
# Run from 23127379_Homework/HW4/ directory
# Search for sleep/waitForTimeout in spec
grep -n "waitForTimeout\|sleep\|setTimeout" Pool-[X]_FR##/fr##.spec.ts
```

| Found Pattern | Action Required |
|-------------|----------------|
| `page.waitForTimeout(N)` where N > 500 | **Replace** with `expect(locator).toBeVisible({ timeout: N })` |
| `page.waitForTimeout(N)` where N ≤ 500 | Tolerated but must be commented explaining why |
| `await new Promise(r => setTimeout(r, N))` | **Replace immediately** |
| Missing `await` before expect/action | **Fix immediately — race condition** |

### Check 5 — Test Isolation

For each `test()` block, verify:

```
□ beforeEach/beforeAll sets up required state via UI navigation
□ afterEach/afterAll cleans up created data via UI (navigate and undo)
□ Test does not rely on state from a previous test
□ Tests can run in random order without failures
□ No API calls used — all setup and teardown performed through the browser UI
```

**Document isolation issues:**
```markdown
### [ISSUE] Test Order Dependency — Test: TC-FR15-EP-003
- **Problem:** TC-EP-003 (Edit product) assumes the product created in TC-EP-001 still exists
- **Fix:** Add `beforeEach` that creates a test product via the **Admin UI** (navigate to admin, fill form, submit) instead of assuming a pre-existing product.
- **Why AI failed:** AI wrote tests assuming sequential execution; did not consider parallel runners
```

### Check 6 — TC Coverage Completeness

Cross-check against HW2 TCs:

```
□ All selected TCs (from Step 1 of AutomationScriptGen) have a corresponding test() block
□ Each test() title contains the TC ID (e.g., "TC-FR06-EP-001")
□ All CANNOT AUTOMATE items are documented in this review file
□ Known-bug TCs are annotated and included (not skipped)
```

### Check 7 — Known Bug Handling

Verify each known-bug TC:

```
□ TC asserts the spec-correct expected result (not the buggy actual behavior)
□ Inline comment present: "// Known bug: BUG-FR##-XXX — expected to fail"
□ Bug is listed in "Known Failures" section of this review
□ Bug is also added to bug_report.md (HITL action)
```
