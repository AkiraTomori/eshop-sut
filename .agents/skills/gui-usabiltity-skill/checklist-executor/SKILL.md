# Checklist Executor

## Purpose

This skill automates the process of executing a GUI testing checklist against
specific screens of a web application (EMS). It produces per-screen execution
results and structured bug reports ready for submission.

## Prerequisites

- A completed GUI checklist file (default: `shared-gui-checklist.md` generated by `gui-checklist-builder`)
- The target screens to test (identified by Scenario and Screen IDs, e.g., A1, A2, B3)
- Access to the SUT (EMS web application)

## Workflow

### Step 1 — Load Checklist & Identify Screens

1. **Read the checklist** from the specified file (default: `shared-gui-checklist.md`).
2. **Confirm the scenario** the user is assigned to (A, B, C, or D).
3. **List the screens** to test (minimum 3). For each screen, confirm:
   - Screen ID and name (e.g., `A2 — Add/Edit Event Form`)
   - URL path within EMS
   - Key UI elements present on this screen

### Step 2 — Execute Checklist Per Screen

For each screen, go through every checklist item and determine:

1. **Status**: `Passed` ✅ or `Failed` ❌
2. **Notes** (required for Failed items):
   - What specifically failed
   - Expected behaviour vs actual behaviour
   - Affected UI element/widget
3. **Screenshot reference** (required for Failed items):
   - File name pattern: `{ScreenID}_{ChecklistID}_fail.png`
   - Example: `A2_IA-02-003_fail.png`

#### Execution Guidelines

- Test each item **literally as described** in the checklist — do not interpret loosely.
- For items that reference a specific widget not present on the current screen, mark as `N/A` (Not Applicable) with a note explaining why.
- For items that require interaction (e.g., "submit form with blank required field"), **actually perform the interaction** and observe the result.
- Use browser DevTools for checks that need inspection (contrast ratios, ARIA attributes, focus order).

### Step 3 — Generate Execution Result Tables

For each screen, produce a Markdown table with columns:

```markdown
| Checklist ID | Description (abbreviated) | Status | Notes |
```

Then produce a summary:
- Total items executed
- Passed count
- Failed count
- N/A count
- Pass rate (%)

### Step 4 — Generate Bug Reports

For each **Failed** item, create a structured bug report:

```markdown
### Bug #{sequential_number}

| Field | Value |
|-------|-------|
| **Bug ID** | BUG-{ScreenID}-{NNN} |
| **Screen** | {Screen name and ID} |
| **Checklist Item** | {Checklist ID} — {abbreviated description} |
| **Steps to Reproduce** | 1. Navigate to... 2. ... 3. ... |
| **Expected Result** | {What should happen} |
| **Actual Result** | {What actually happens} |
| **Severity** | {1=Cosmetic, 2=Minor, 3=Major, 4=Critical} |
| **Screenshot** | `{screenshot_filename}` |
| **Type** | Bug |
```

#### Severity Scale

| Level | Name | Description |
|-------|------|-------------|
| 1 | Cosmetic | Visual imperfection that doesn't affect functionality |
| 2 | Minor | Minor functional issue with easy workaround |
| 3 | Major | Significant functional issue, difficult workaround |
| 4 | Critical | Blocks core functionality, no workaround |

### Step 5 — Output Deliverables

Generate the following files in the Artifacts directory:

1. **`checklist-execution-{ScreenID}.md`** — Per-screen execution result table for each screen tested
2. **`bug-reports.md`** — All bug reports consolidated
3. **`execution-summary.md`** — Overall summary across all screens:
   - Table comparing pass rates across screens
   - Most common failure categories (by IA aspect)
   - Distribution of bugs by severity

### Step 6 — Log to AI Audit

After execution, invoke `ai-audit-logger` to record:
- Tool used for analysis
- Date/time of execution
- Screens tested
- Summary of findings

## Integration with Other Skills

- **Input from**: `gui-checklist-builder` (the checklist to execute)
- **Output to**: `report-assembler` (execution results + bug reports)
- **Logs to**: `ai-audit-logger` (AI interaction records)

## Tips for Effective Execution

1. **Test in order**: Go through IA-01 → IA-02 → IA-03 → IA-04 for each screen
2. **Screenshot immediately**: Capture evidence for failed items right away (EMS data may reset)
3. **Note the browser state**: Record browser, OS, viewport size used during testing
4. **Be specific in notes**: "Button text truncated at 768px viewport" is better than "Layout broken"
5. **Cross-reference**: If a failure relates to a usability issue, note this for Task 2
